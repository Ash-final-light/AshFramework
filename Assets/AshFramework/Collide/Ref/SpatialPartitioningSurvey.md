## 1. 调查结论

空间索引的选择首先取决于对象尺寸分布、空间密度、移动方式和查询类型。不存在对所有场景都最快的结构。

本项目已确定提供松散四叉树和空间哈希。以下通用对照用于理解技术适用边界；本项目两种实现的具体参数与使用场景通过第 8 节的评测确定。

| 需求特征 | 建议优先评估 | 主要原因 | 必须关注 |
| --- | --- | --- | --- |
| 大量尺寸接近的移动单位、弹幕、局部邻域查询 | 均匀网格 / 空间哈希 | 结构简单，易批量重建，便于连续存储 | 热点聚集、格长、大对象跨格 |
| 大小差异明显的动态碰撞体，需范围查询及射线查询 | 动态 AABB 树 | 按物体组织，不要求统一格长 | 树质量、重插频率、包围盒膨胀 |
| 密度不均的二维场景，需分区调试或区域管理 | 四叉树 / 松散四叉树 | 层次和区域直观，可自适应细分 | 跨边界对象、父节点滞留、深度限制 |
| 真正三维的稀疏空间或体素层次 | 八叉树 / 松散八叉树 | 与三维区域层次一致 | 节点数量、分配开销、根节点边界 |
| 静态三角网格，重复射线或形状查询 | 静态 BVH；必要时比较空间型 k-d 树 | 可用较高构建成本换取后续查询效率 | 构建时间、内存、几何更新方式 |
| 低维点集的最近邻 / kNN | 点型 k-d 树 | 围绕距离剪枝组织点集 | 动态重建、高维退化、点与实体的区别 |
| 多数对象静止或相邻帧排序变化小 | SAP | 能利用时间相干性 | 投影重叠、瞬移、频繁增删 |
| 地理区域、编辑器矩形、持久化空间数据 | R-tree / R*-tree | 动态范围索引及批量装载较成熟 | 子树包围区域重叠、分裂策略 |

本项目先建立暴力枚举基线，再实现空间哈希与松散四叉树，通过统一输入比较两者。二维游戏和基于地面平面的 3D ARPG 均使用二维索引；具体坐标投影由适配层决定。当前没有本项目实测排名，不预设某个方案在所有关卡中更快。

## 2. 概念边界与基本约束

### 2.1 三类容易混淆的方法

| 类别 | 划分或组织的对象 | 代表方法 | 关键性质 |
| --- | --- | --- | --- |
| 空间划分 Spatial Subdivision | 空间区域 | 网格、四叉树、八叉树、k-d 树、BSP | 区域可互不重叠，但跨区域物体可能需要多处引用 |
| 物体划分 Object Subdivision | 几何对象集合 | 常规 BVH、动态 AABB 树 | 子节点包围体可以重叠；常规实现每个代理只存一份 |
| 排序与投影剪枝 | 各轴上的对象区间 | SAP / Sweep and Prune | 依靠区间排序筛掉不可能相交的对象对 |

R-tree 也是以对象包围区域组织的空间索引，不属于把整个空间切成不相交单元的严格空间划分。空间哈希则通常是稀疏网格的存储方式，哈希本身不决定几何划分。BVH 的空间分裂变体可能复制几何引用，不能把“每个物体只出现一次”推广到所有 BVH。参见 [PBRT：BVH](https://pbr-book.org/4ed/Primitives_and_Intersection_Acceleration/Bounding_Volume_Hierarchies)、[Boost.Geometry：空间索引](https://www.boost.org/doc/libs/latest/libs/geometry/doc/html/geometry/spatial_indexes/introduction.html)。

### 2.2 在碰撞流水线中的位置

```text
对象状态 → 保守包围体 → 索引更新 → 宽相候选对
                                 ↓
                       层级/规则过滤与精确窄相
                                 ↓
                         接触、触发器或业务结果
```

宽相 Broad Phase 只需保守排除不可能碰撞的对象；窄相 Narrow Phase 才计算真实相交、距离或接触信息。AABB 重叠通常只是候选条件。SAT、GJK、EPA 属于几何检测或接触计算方法，不是空间划分技术。NVIDIA 对宽相与窄相职责的说明见 [GPU Gems 3，第 32 章](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-32-broad-phase-collision-detection-cuda)。

工程上应明确以下正确性契约：

1. 对指定时刻、包围体及过滤规则，所有真实相交对必须包含在候选对中；允许假阳性，不允许漏检。
2. 若需要连续碰撞检测，索引的保守范围须覆盖运动过程；仅索引帧末 AABB 会遗漏高速穿越。
3. 静态对象与动态对象可使用不同索引，但需要明确枚举动态–动态、动态–静态以及业务是否需要静态–静态。
4. 增量宽相若只查询“本帧移动代理”，必须维护已有候选/接触对；否则静止后持续相交的对象会从结果中消失。

### 2.3 如何理解复杂度

下文记 `N` 为对象数量，`K` 为唯一候选对数，`R` 为对象在所有单元中的引用总数，`V` 为单次查询访问的节点数，`C` 为单次查询扫描的原始对象引用数，`k` 为该次输出数量。

输出 `K` 对至少需要 `Ω(K)` 时间。如果所有包围体彼此重叠，`K = N(N−1)/2`，任何完整输出候选对的算法都无法消除这部分二次开销。“平均 O(N)”或“查询 O(log N)”需要分布、树高及局部占用等前提，不能当作无条件保证。

## 3. 网格系列

### 3.1 均匀网格 Uniform Grid

**原理。** 使用固定格长 `h` 对空间离散化，将对象关联到覆盖的格子。相同或必要邻接格中的对象才形成候选。网格适合局部交互，工程代价主要由跨格引用和单格占用决定。原理参考 [NVIDIA：Spatial Subdivision](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-32-broad-phase-collision-detection-cuda)。

**工程实现可选择两种策略，不能混用它们的邻域假设：**

- **中心入格：** 一个对象只放入中心所在格。必须根据对象最大尺寸和查询距离推导邻域；只有满足相应尺寸约束时，二维 3×3 或三维 3×3×3 邻域才足够。
- **包围体覆盖入格：** 把 AABB 放入所有覆盖格，查询也遍历查询 AABB 的覆盖格。采用一致边界规则时，相交对象共享至少一个格子；需要对跨格出现的同一对象对去重。

推荐先采用覆盖入格，原因是容易用暴力 AABB 检测证明完整性；如果大对象使 `R` 过高，再考虑大对象旁路或分层结构。

**坐标规则建议。** 对每一轴使用 `cell = floor((position − origin) / h)`，且 `h > 0`。负坐标不能向零截断，例如 `−0.1 / 1` 的格坐标应为 `−1`。若把边界接触也视为相交，覆盖区间可保守使用 `floor(min)` 到 `floor(max)`，两端均包含；恰好位于格线的上界会多占格，但便于保持保守性。不要随意给上界减 epsilon，否则可能丢失接触候选。

**成本。** 构建的对象写入成本为 `O(R)`，还需考虑单元清空和分配。若第 `c` 个格有 `m_c` 个引用，在每格内枚举对象对的原始成本与 `Σ m_c(m_c−1)/2` 成正比，去重前可能远大于 `K`。

**优点。** 易理解、易调试，数组或排序后的格记录便于连续访问和批量处理。

**缺点。** 格子过大增加格内两两检查，过小增加跨格引用；对象密集聚到同一格时退化。直接为整个大世界分配稠密数组还会浪费空格内存。

### 3.2 空间哈希 Spatial Hashing

**原理。** 通过整数格坐标定位哈希容器，只存活跃格；无需给空旷区域预留完整网格。Teschner 等的原始研究讨论了格长、哈希函数及表大小对碰撞检测的影响，见 [2003 年论文](https://cgl.ethz.ch/Downloads/Publications/Papers/2003/Tes03/Tes03.pdf)。

**工程实现需要区分：**

| 容器方案 | 对不同格坐标发生相同哈希值的处理 | 适用考虑 |
| --- | --- | --- |
| 以完整格坐标为键的字典 | 哈希后继续比较坐标相等性 | 首版易验证，关注桶及列表的分配 |
| 固定容量哈希桶 | 桶内保留原格坐标，或保守处理桶内所有记录 | 容量可控，必须处理拥挤和溢出 |
| 排序后的格记录 | 按完整格键排序，再构建连续区间 | 适合批量重建，比较排序通常需 `O(R log R)` |

哈希值相同不代表空间格相同。覆盖写入旧记录、丢弃溢出项或把哈希值误当唯一格 ID 都可能漏检；保守地把碰撞桶全部当候选则只会增加假阳性。

**成本。** 哈希负载适宜时，构建期望为 `O(R)`；局部查询约为查找覆盖格并扫描 `C` 个引用的成本，加去重和输出。该期望不覆盖严重哈希冲突、容量增长和密集格的两两枚举。

**适合。** 大范围稀疏世界、尺寸接近且移动频繁的单位、弹幕、局部技能查询。最近邻可以实现，但需要扩张搜索范围和基于未访问区域距离下界的停止条件，不能只返回本格最近对象。

**风险。** 多格对象重复、字典扩容、每格列表产生垃圾、大坐标溢出。首次实现宜保留完整整数坐标，避免未经范围证明的位打包。

### 3.3 分层网格 / 分层空间哈希 Hierarchical Grid / HGrid

**原理。** 使用多种格长，例如 `h_l = h_0 × 2^l`，按包围体尺寸把对象分配到合适层级，以减少大对象在细网格中的重复覆盖。参考 [Schornbaum：Hierarchical Hash Grids for Coarse Collision Detection，2009](https://www10.cs.fau.de/publications/theses/2009/Schornbaum_SA_2009.pdf)。

**工程取舍。** 小对象查询不能只检查同层；必须处理可能相交的粗层对象。需要证明跨层查询范围和唯一配对规则，例如统一由细层对象查询相关粗层、同层再按对象 ID 排序生成候选。具体覆盖范围取决于采用中心入格还是覆盖入格，以及各层尺寸约束，不能直接套固定邻域。

**优点。** 对象尺寸差异大时，可能显著降低 `R`。

**缺点。** 层数、跨层扫描及尺寸改变后的迁移增加实现复杂度。不能把某篇论文在特定假设下的平均线性结果作为任意负载保证。

**建议。** 先记录单层哈希的大对象跨格成本，证明它是瓶颈后再评估；也可先用“小对象网格 + 大对象列表/树”的简单混合结构。

## 4. 递归空间划分树

### 4.1 四叉树 Quadtree

**原理。** 二维区域递归分成四个子区域，常按容量、深度或最小单元尺寸停止细分。需区分区域四叉树、点四叉树等变体；这里主要讨论固定中点切分区域、存储对象包围体的形式。定义及细分机制参考 [CGAL：Quadtrees, Octrees, and Orthtrees](https://doc.cgal.org/latest/Orthtree/index.html)。

**工程上存储有面积的物体时有三种常见方式：**

| 跨边界处理 | 收益 | 代价及查询要求 |
| --- | --- | --- |
| 保留在能完整容纳它的最深节点 | 每个物体一份 | 查询必须检查途经的内部节点对象；分界线附近可能积累大量对象 |
| 复制到所有相交叶节点 | 查询逻辑局部化 | 引用和迁移成本增加，必须去重 |
| 使用松散节点 | 减少部分边界引起的滞留与迁移 | 查询按松散包围范围剪枝，详见 4.3 |

**适合。** 二维分布不均、局部区域查询、需要直观空间分区的业务。

**风险。** 重合点或极端聚集导致持续细分；必须设置最大深度、最小尺寸和分裂/合并阈值。若动态物体频繁跨边界，树维护成本可能超过查询节省。仅比较同一叶内对象会漏掉父节点对象与后代对象之间的碰撞。

### 4.2 八叉树 Octree

**原理。** 四叉树的三维对应形式，每次分成八个子区域；适用三维区域管理、稀疏体素和空间查询。定义参考 [CGAL Orthtree 手册](https://doc.cgal.org/latest/Orthtree/index.html)。

**工程取舍。** 深度为 `d` 的完整八叉树叶数为 `8^d`，实际应按需创建非空节点。对于高度方向变化很小的地面单位，三维细分未必值得，可比较 XZ 平面索引加高度过滤；存在上下楼层时，平面过滤只能用于宽相，最终仍需正确的三维检测。

跨节点对象的处理与四叉树相同。还需定义越过根范围时的行为：扩根、分块或转入旁路集合；不能直接忽略越界对象。

### 4.3 松散四叉树 / 松散八叉树 Loose Quadtree / Octree

**原理。** 保留规则区域层次，但把节点的有效包围范围适当放大，使相邻节点范围重叠，从而让一定尺寸的对象更容易由单个节点容纳。经典实现说明见 [Thatcher Ulrich：Notes on Spatial Partitioning](https://tulrich.com/geekstuff/partitioning.html)。

**工程建议。** 若采用松散范围内可继续驻留的更新策略，小幅移动可能无需迁移。查询必须与节点的松散范围做相交判断；若仍用原始格范围剪枝，会漏掉伸出原区域的对象。

松散系数越大，潜在迁移越少，但查询时访问的重叠子树可能越多。对象归属、驻留条件和节点扩张规则必须一起设计，不能认为“跨原格线后永远不用更新”。不要机械预分配所有深度节点。

### 4.4 k-d 树 k-Dimensional Tree

**原理。** 每次用一个轴对齐超平面把当前区域分成两部分，可依据数据分布选择切分轴和位置。

必须区分两种使用方式：

- **点型 k-d 树：** 存储低维点集，做最近邻、kNN 和范围检索。距离下界决定是否访问另一子树。功能参考 [CGAL：Spatial Searching](https://doc.cgal.org/latest/Spatial_searching/index.html)。
- **空间型 k-d 树：** 用于几何射线加速，跨切分面的三角形等图元可能在两侧都有引用。构建与遍历示例参考 [PBRT 第三版：Kd-Tree Accelerator](https://pbr-book.org/3ed-2018/Primitives_and_Intersection_Acceleration/Kd-Tree_Accelerator)。

**工程取舍。** 静态或批次更新的点集较易维护；高频移动可能破坏已有划分质量，需重建或使用专门动态变体。精确最近邻最坏仍可能扫描大量数据，高维时剪枝也可能失效。不能只把碰撞体中心放进点树，再用未考虑半径的点距离排除实体碰撞。

### 4.5 BSP Binary Space Partitioning

**原理。** 用一般方向的超平面递归切分空间。二维切分线、三维切分平面均可不与坐标轴对齐；k-d 树可视为轴对齐的特化。区域表达和树操作示例见 [Apache Commons Geometry：BSP Tree Tutorial](https://commons.apache.org/proper/commons-geometry/tutorials/bsp-tree.html)。

**适合。** 静态建筑几何、实体区域表达、布尔运算及需要平面边界语义的场景。

**工程取舍。** 能贴合斜面几何，但切分面选择、跨面图元拆分、数值容差与拓扑一致性复杂。频繁改变几何布局时维护代价较高；作为普通动态单位碰撞宽相的首版方案，验证成本通常偏高。

## 5. 包围体层次与动态范围索引

### 5.1 静态 BVH Bounding Volume Hierarchy

**原理。** 对物体或图元集合分组，父节点包围体包住全部子节点。查询与父节点不相交时跳过整棵子树。常规对象划分 BVH 不要求子包围体互斥；可按中点、中位数、表面积启发式 SAH 或 Morton 排序等方法构建。原理及构建方案见 [PBRT 第四版：Bounding Volume Hierarchies](https://pbr-book.org/4ed/Primitives_and_Intersection_Acceleration/Bounding_Volume_Hierarchies)。

**工程取舍。** 适合静态三角网格和重复射线查询。图元移动后，可保持拓扑并自底向上更新包围体，即 refit；但大幅移动可能使子树严重重叠，后续需局部优化或重建。构建快不等于查询快，应测量完整使用周期。

射线场景中适用的 SAH 代价模型，不一定就是对象对枚举和范围查询的最佳模型。若用于碰撞自查询，需要正确遍历可能相交的节点对并避免重复，而非只实现一条射线的遍历。

### 5.2 动态 AABB 树 Dynamic AABB Tree

**原理。** 以碰撞代理为叶节点维护可增删的 AABB 层次，支持范围、射线等查询。Box2D 提供二叉动态 AABB 树，并使用节点池和索引组织节点，可作为实现参考；见 [Box2D：Dynamic Tree](https://box2d.org/documentation/group__tree.html)。该参考不等同于本项目 Unity 内部的具体版本实现。

**常见工程策略。** 为代理保留略大的包围盒，即 fat AABB；真实 AABB 仍被它包含时，可暂缓树中代理的重插。需要重插时选择兄弟节点，更新祖先包围体，并采用平衡、局部旋转或重建策略控制树质量。fat AABB 是可选维护策略，不能假定外部库任一版本都自动采用相同规则。

**优点。** 对尺寸差异和非均匀分布通常比单一格长更容易处理；查询方式灵活。

**风险。** 过大的 fat AABB 增加假阳性；过小会频繁重插。树高不是唯一质量指标，还要统计内部包围体重叠、访问节点和候选数。若只查询移动代理，必须结合第 2.2 节的持久配对规则。

### 5.3 R-tree / R*-tree

**原理。** 用多路树组织对象的最小包围矩形或包围盒，支持插入、删除、范围和邻近查询。R*-tree 通过更复杂的组织策略优化节点重叠等指标；不同分裂策略在更新和查询之间取舍。参考 [Boost.Geometry 官方说明](https://www.boost.org/doc/libs/latest/libs/geometry/doc/html/geometry/spatial_indexes/introduction.html)。

**适合。** 地理数据、编辑器对象、地图区域以及较偏查询的数据集；静态批量装载也有意义。

**工程取舍。** 子区域重叠会扩大遍历范围。高频移动意味着持续维护索引，不能直接依据数据库或静态数据测试认定它适合每帧全动态物理。建议仅在确有多路范围索引需求时进入候选名单。

## 6. SAP、混合方案与相关编码

### 6.1 SAP Sweep and Prune / Sort and Sweep

**原理。** 将 AABB 投影到轴上，对最小/最大端点排序，用扫描活动集合产生区间重叠对，再检查其他轴。相邻帧顺序接近时可增量维护排序；参考 [NVIDIA：Sort and Sweep](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-32-broad-phase-collision-detection-cuda)。

**工程取舍。** 常规比较排序加单轴扫描可表示为 `O(N log N + P)`，`P` 是所选轴上的区间重叠对数；`P` 可能远大于最终三维候选数。增量插入排序成本与端点逆序数量有关，瞬移或大量乱序可能达到二次级别。对象大量投影到同一区间时，活动集合配对也会退化。

边界接触若算重叠，同位置端点的处理顺序必须让“开始”先于“结束”，或采用等价的闭区间规则，否则会漏掉接触候选。

### 6.2 混合方案

以下为可评估的组合，不是本次实现内容：

- **静态 BVH + 动态哈希/树：** 静态几何离线或低频构建，动态对象使用更便宜的更新结构。
- **小对象网格 + 大对象树：** 避免超大 AABB 覆盖海量细格；必须补齐两类对象之间的查询。
- **世界分块 + 块内索引：** 限制每次局部查询范围；跨块物体、跨块射线和相邻边界必须保守处理。
- **网格 + SAP：** 先分区，再在局部运行排序剪枝。Unity 2022.3 的 Multibox Pruning 即采用网格与格内 SAP，Automatic Box Pruning 还自动计算边界和划分，见 [Unity 2022.3 Physics 设置](https://docs.unity3d.com/2022.3/Documentation/Manual/class-PhysicsManager.html)。

### 6.3 Morton / Z-order 与 Hilbert 编码的位置

它们用于把多维位置映射到一维顺序，可辅助排序、局部性和树构建，不是可以独立保证碰撞完整性的检测算法。PBRT 的 Morton 编码与 HLBVH 构建见 [BVH 章节](https://pbr-book.org/4ed/Primitives_and_Intersection_Acceleration/Bounding_Volume_Hierarchies)。

工程上不能只比较相邻若干个 Morton 编码对象就认为找全碰撞对；还需要有证明的区间覆盖、树遍历或其他查询规则。坐标量化范围、编码位宽和相同编码对象的处理也应明确定义。Hilbert 编码在此仅列为相关编码方向，本次不展开其构造及性能比较。

## 7. 成本与实现难度对照

下表是工程分析，不是跑分结果。内存、构建和更新均依具体存储及算法变化；难度是相对本模块首版实现而言。

| 技术 | 维护 / 构建成本的观察方式 | 查询 / 候选成本的观察方式 | 首版难度 |
| --- | --- | --- | --- |
| 均匀网格 | `O(R)` 写入，另计稠密格初始化 | 扫描覆盖格和 `C` 条引用；格内配对受 `Σm_c²` 支配 | 低 |
| 空间哈希 | 良好负载下期望 `O(R)`；排序型另计排序 | 格查找、引用扫描和去重；热点仍可二次退化 | 低～中 |
| 分层网格 | 对象迁层及各层记录维护 | 同层与跨层范围都必须覆盖 | 中～高 |
| 四叉树 / 八叉树 | 路径深度、分裂合并、跨区引用数 | 访问节点与节点内扫描；最坏可扫描全量 | 中 |
| 松散树 | 增加松散范围，比较迁移节省与维护成本 | 重叠范围增加 `V` 和候选 | 中 |
| 点型 k-d 树 | 常见平衡构建约 `O(N log N)`，取决于分割实现 | 低维且分布适宜时剪枝有效；最坏 `O(N)` | 中 |
| 空间型 k-d / BSP | 分割面选择、跨面引用或图元拆分 | 与空间分布及遍历路径强相关 | 高 |
| 常规 BVH | 构建策略不同；固定拓扑 refit 可线性遍历节点 | `O(V + k)` 是遍历表达，`V` 最坏可达 `O(N)` | 中～高 |
| 动态 AABB 树 | 插入/删除/重插随树高和启发式变化 | 节点重叠与树质量决定 `V`；无普适对数保证 | 高 |
| R-tree / R*-tree | 分裂、重插、批量装载策略相关 | 受包围区域重叠与输出量影响 | 高 |
| SAP | 比较排序 `O(N log N)`；增量维护看逆序数 | 所选轴重叠对 `P`，最坏 `O(N²)` | 中 |

常规固定分支数、每个对象只存一次的树，其节点存储通常为线性量级；稠密网格要计全部分配格数，复制式空间树要计重复引用。仅使用 `O(N)` 无法比较实际内存峰值。

## 8. 面向 AshFramework 的双方案设计与验证建议

### 8.1 已确认范围与坐标约定

用户已确认：粗筛在运行时选择松散四叉树或空间哈希，用于平面 3D ARPG 和 2D 游戏。以下为据此提出的设计建议，不是已有 API、类型或已经实现的能力。

| 使用场景 | 建议默认索引平面 | 索引输入 | 额外维度的职责 |
| --- | --- | --- | --- |
| 平面 3D ARPG | 世界 XZ | 世界包围体投影后的二维 AABB | 按 1/2/3 逻辑高度集合过滤；需要时另加楼层规则 |
| 常规 2D 游戏 | 世界 XY | 世界包围体对应的二维 AABB | Z 可作为显示深度；如有游戏逻辑分层则显式定义规则 |

XY/XZ 是建议默认值，具体游戏可以选择自己的逻辑平面。投影适配层负责将世界包围体变成二维范围，两种索引只接收一致的平面数据。应投影完整的保守包围体，不能仅投影中心或使用未处理旋转的局部尺寸。

对保守 3D 包围体，真实三维相交必然意味着 XZ 投影相交，因此二维粗筛可保留三维碰撞所需候选；反过来不成立。上下楼层、跳跃和飞行可能具有相同 XZ 位置，应按游戏语义追加高度区间、楼层/碰撞层和真实形状判断。若玩法刻意采用纯地面判定，则可不按模型 Y 高度过滤；此时是明确的玩法规则。

```text
世界对象与真实形状
        ↓ 世界包围体和坐标投影
统一二维代理数据 + 可选高度/碰撞层数据
        ↓ 运行时配置选择
松散四叉树                 空间哈希
        ↓ 相同语义的二维粗筛候选
公共过滤：真实二维 AABB、碰撞规则、可选高度
        ↓
按玩法执行二维 / 三维窄相与事件处理
```

### 8.2 公共语义与运行时选择

**职责划分建议：** 由碰撞世界或同等上层对象持有权威代理数据和稳定对象 ID；由选中的索引维护内部节点/格记录。插入、删除、更新、二维范围查询和完整候选对生成属于共同操作；最近邻和射线按后续实际需求扩展，并分别定义完整性契约。

两种实现应统一以下行为：

1. 接收同一份保守二维 AABB，采用相同的边界接触、无效范围和浮点容差规则。
2. 插入、移除、禁用、尺寸变化、瞬移和碰撞规则变化后，下一次约定查询阶段可见一致状态。
3. 范围查询返回的原始候选允许不同；经过公共真实 AABB 和规则过滤后，结果集合必须一致。
4. 对象查询结果不重复；完整候选对规范化为稳定 ID 的有序二元组，去掉自身配对和重复对。
5. 输出缓冲不足时扩容、重试或显式失败，不能静默截断。需要确定顺序时，在公共层按稳定 ID 排序。
6. Enter/Stay/Exit 和业务状态由公共层管理，避免同一物体在不同索引中表现出不同碰撞生命周期。

**运行时选择：** 建议每个碰撞世界初始化或关卡加载时读取配置并创建一个索引实现。配置包括实现种类与各自参数；XY/XZ 投影模式属于世界配置，与索引种类独立。多个碰撞世界可以分别选择实现。这里的运行时选择不要求每帧自动判断或同时维护两套索引。

**若后续需要游戏运行中切换：** 在模拟步之间暂停索引写入，基于同一权威数据快照构建目标索引；构建期间可缓冲变更，或保持该同步阶段不发生变更。目标准备完成后统一替换索引，保留对象 ID、过滤规则和公共接触状态，再释放旧索引。内部节点号、格记录位置等句柄不能充当外部对象身份。

切换本身不应产生虚假的 Exit/Enter；仍需按切换后的真实对象状态正常结算事件。切换成本包括重建时间、临时内存和可能的帧尖峰，应单独测量。无明确性能证据时，先采用显式配置选择。

### 8.3 两种实现的具体约束

| 项目 | 松散四叉树 | 空间哈希 |
| --- | --- | --- |
| 首版存储策略 | 每个代理存于一个能完整容纳其 AABB 的节点 | AABB 覆盖入格，完整二维整数格坐标作键 |
| 空间范围 | 定义初始根范围与越界扩根/重建规则 | 稀疏格可按需创建，明确坐标数值范围 |
| 更新条件 | 不再被驻留节点松散范围包含时迁移；增删及尺寸变化同样处理 | 覆盖格集合变化时更新记录；真实 AABB 仍须始终同步 |
| 查询剪枝 | 使用松散节点范围，并检查访问节点自身存放的对象 | 遍历查询 AABB 覆盖格，扫描格内引用 |
| 去重 | 每代理单份，但全配对仍需规范化对象对 | 单次查询及全配对均需处理跨格重复 |
| 主要参数 | 根范围、松散系数、最大深度、节点容量、分裂/合并条件 | 格长、初始容量、记录及结果缓冲容量 |
| 主要统计 | 节点访问、内部节点对象数、迁移/扩根次数、候选数 | 格占用分布、最大格占用、`R/N`、重复引用和候选数 |

**松散四叉树的关键约束：** 定义松散系数为“松散节点边长 / 基础节点边长”，取值不小于 1，避免参数含义混乱。子树可达的所有对象必须被用于剪枝的祖先范围保守包含；维护、扩根和驻留策略都要保持这个不变量。节点的兄弟松散区域会重叠，不能只比较同一叶中的对象，也不能只按查询中心选择一条分支。首版可对每个对象查询整棵树并按稳定 ID 限制配对方向，先保证完整性，再优化节点对遍历。

**空间哈希的关键约束：** 使用 `floor` 处理负坐标，按闭区间约定保守覆盖格边界。哈希相同仍需比较完整格坐标；多格引用通过查询戳或临时集合等方式去重，具体手段须处理戳回绕和对象 ID 复用。超大对象可能产生大量格引用，首版应检测并显式处理容量需求；若采用独立大对象列表，必须补齐与所有普通对象的配对及查询，不能通过固定跨格上限丢弃记录。

**选择建议的适用前提：** 尺寸较接近、移动频繁、局部查询多的负载可先测空间哈希；密度差异较大或需要区域层次调试的负载可重点测松散四叉树。对极端聚集、巨大范围查询和尺寸跨度，两者都可能有明显成本，不能只按“3D 用树、2D 用哈希”选择。两种游戏都可以使用任一实现。

### 8.4 建议实现顺序

1. **公共数据与暴力基线：** 明确平面投影、二维 AABB、稳定 ID、过滤和更新阶段，用暴力枚举作为正确性对照。
2. **空间哈希：** 覆盖入格与完整坐标键，先完成增删改查、去重、边界与容量处理。
3. **松散四叉树：** 使用同一份代理输入和查询语义，完成驻留、迁移、分裂、越界处理与保守遍历。
4. **配置选择：** 由碰撞世界统一创建选中的实现，业务逻辑调用公共操作；游戏中途热切换按实际需求单独实现。
5. **联合验收与优化：** 两种实现分别对照暴力结果，并相互比较经过公共过滤后的结果；随后再优化池化、连续存储及并行处理。

暴力枚举是测试与诊断基线；面向游戏运行的正式粗筛选项保持为用户确定的两种方案。

### 8.5 建议评测矩阵

以下为待执行方案，未运行，也没有对应性能结论：

| 维度 | 建议样例 |
| --- | --- |
| 对象规模 | 100、1,000、10,000；资源允许时扩大，暴力对照可单独限制规模 |
| 尺寸分布 | 等尺寸；最大/最小边长比 10 倍、100 倍；少量超大对象 |
| 空间分布 | 均匀、多个聚簇、狭长通道、空旷稀疏、全部包围体重叠 |
| 动态比例 | 0%、10%、100% 移动；叠加少量瞬移和批量增删 |
| 查询类型 | 全配对、小范围、大范围、短/长射线；有需求时单独测 kNN |
| 网格参数 | 格长相对典型边长的 0.5、1、2、4 倍，结合跨格策略解释 |
| 松散树参数 | 松散系数 1、1.5、2；组合不同容量、深度及根范围，分别记录维护与查询成本 |
| 边界输入 | 负坐标、格线接触、零尺寸 AABB、重合对象、根边界外对象 |
| 游戏空间 | 相同二维输入分别由 XY 与 XZ 适配生成；加入同 XZ 不同高度、跨楼层和跳跃用例 |
| 实现切换 | 同一快照切换前后经公共过滤的结果一致；若支持热切换，测量变更缓冲、事件连续性和峰值内存 |

**记录指标：** 构建、增量更新、候选生成、去重及窄相时间分别计时；报告总耗时、P50/P95、唯一候选数、原始重复对数、节点/格访问数、`R/N`、峰值内存和 GC 分配。候选倍率用“唯一候选对数 / 暴力 AABB 重叠对数”，分母为零时单列绝对数。

**正确性验收：** 固定随机种子和完整输入记录。相同过滤条件下，暴力 AABB 重叠对集合必须是候选集的子集；再对候选执行相同 AABB 检测，结果应与暴力集合相等。候选层可能使用 fat AABB 等更松的界，不能要求原始候选集直接等于真实重叠集。

若还需验证真实形状碰撞，另以独立窄相基线比对；AABB 对照只验证宽相保守性。连续碰撞需另建运动路径用例，包括高速穿越及旋转中间姿态。对于纯平移刚体，起止 AABB 的并集可覆盖平移扫掠；含旋转或形变时，两端并集不一定覆盖整个过程。

树结构额外检查父包围体包含子节点、对象引用完整性和有效句柄；网格结构检查覆盖格集合、移除后的残留引用及哈希冲突。若要求确定性，对候选按稳定对象 ID 规范化和排序，并测试插入顺序变化。

双方案专项验收应覆盖：对象分别在兄弟松散节点内但实际相交；对象停留在原始节点范围外、松散范围内；对象跨越根边界；同一对对象共享多个哈希格；哈希冲突；禁用/删除/句柄复用；高度变化但二维范围不变。两种实现必须各自通过同一暴力基线，不能仅以二者互相一致证明正确。

在同一项目、目标平台和构建配置下比较，预热后进行多次采样。Editor 数据只作为开发阶段参考；最终还需目标设备构建验证。对象 ID 和分布应固定，避免把输入变化误判为结构收益。

### 8.6 Unity 集成注意事项

- 本项目 Unity 版本为 2022.3。内置 3D Physics 提供 SAP、Multibox Pruning 和 Automatic Box Pruning 设置；它们属于内置物理模拟配置，不会自动成为自定义 `Collide` 的索引。2D Physics 的设置需单独处理。参考 [Unity 2022.3 Physics 手册](https://docs.unity3d.com/2022.3/Documentation/Manual/class-PhysicsManager.html)。
- 若需求本来只针对 Unity Collider，应先明确现有物理查询能否满足业务，再判断是否需要维护第二套索引。双份索引会增加状态同步和维护成本，这是工程取舍。
- 将索引更新安排在明确的模拟阶段，查询期间保持一致快照；不要混用前一帧格记录和当前帧包围体。
- 连续存储、池化和复用缓冲可作为优化方向；实际选择前先量化 GC 与缓存成本。是否使用 Jobs、Burst 或原生容器需另行确认包、程序集和线程限制，本文不假定项目已具备这些依赖。
- 后续调试可视化应显示格/节点、对象真实 AABB、保守 AABB 和候选对数。本次仅新增调查文档，未创建场景、Prefab、C# 实现或修改物理设置。
